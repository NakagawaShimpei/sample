## 2. 傾向・現象・改善案

### 項目1. r003（第3会議室）の 13時台キャンセル集中

**傾向（事実）**
- r003 の予約12件中8件がキャンセル（キャンセル率 67%）
- キャンセルの大部分が 13:00〜14:00 枠（rh076〜rh083 の8件中6件）
- 設備はホワイトボードのみ。プロジェクター・モニターなし

**現象の説明**
昼食直後の時間帯に予約が集中しているが、社員の昼休み延長・食後の予定変更によりキャンセルが起きやすい。また設備が乏しいため、いざ使おうとすると用途に合わず直前にキャンセルされている可能性が高い。

**改善案**
- 12:30〜13:30 を予約不可枠（ランチバッファ）として設定する
- モニターを1台追加し、基本的な会議用途に対応できるようにする
- または「ホワイトボード作業専用室」として用途を明示し、期待値を下げる

---

### 項目2. r004（大会議室A）での 1on1 常用による大部屋の非効率占有

**傾向（事実）**
- r004 の予約20件中 rh060〜rh067 の連続8件がすべて「1on1」（参加者 1〜3名）
- r004 の定員は 30名。1on1 での使用は定員の 3〜10% しか活用していない
- 同期間に rh087（15名 企画会議）や rh092（18名 週次定例）も r004 を使用

**現象の説明**
最も設備が充実している（プロジェクター・マイク・Web会議システム）ため、少人数でも安易に r004 が選ばれている。その結果、大人数が必要な会議が空きを確保できない競合が発生している可能性がある。

**改善案**
- 予約画面で参加人数が4名以下の場合、r009/r010（ミーティングブース）を優先案内する
- r004 に「大人数推奨：目安5名以上」と注記を表示する
- 1on1 に適した小部屋（r009/r010）の認知を高める運用周知を行う

---

### 項目3. r013（集中ブース1）への定員超過予約

**傾向（事実）**
- rh057：定員1名の集中ブース1（r013）に 7名 での 1on1 を予約 → キャンセル
- db.json の現行予約にも参加者99名での r001（定員10名）予約が存在
- 予約時に定員チェックが機能していない

**現象の説明**
フロントエンドまたは API レベルで参加人数と部屋定員の照合が行われていないため、物理的に不可能な予約が登録できてしまっている。キャンセルで対処されているが、その間は他の利用者が予約できない状態になる。

**改善案**
- 予約フォームで `attendeeCount > room.capacity` の場合にエラーまたは警告を表示する
- API サーバー側でも同条件のバリデーションを追加し、二重防御にする
- 既存の異常データ（参加者99名の予約など）をクレンジングする

---

### 項目4. r007（プロジェクトルーム1）の特定ユーザーによる固定占有

**傾向（事実）**
- rh068〜rh075 の8件がすべて sato による毎週火曜 10:00〜11:00 の週次定例（キャンセルゼロ）
- r007 全体のキャンセル率は 6%（最低水準）
- 同じ設備構成の r008（プロジェクトルーム2）の利用は3件にとどまる

**現象の説明**
同一ユーザーが同一部屋を毎週定期予約することで、事実上の専有状態になっている。r008 は空いているが新規利用者が r007 に集中するため競合リスクがある。定期予約の仕組みがないため、毎週手動で個別予約されていると推測される。

**改善案**
- 繰り返し予約（定期予約）機能を実装し、週次枠を一括で確保・管理できるようにする
- r007/r008 は同等設備のため、空き状況に応じてシステムが自動で振り分ける選択肢を用意する

---

### 項目5. 多数の部屋が履歴ゼロ（42室中29室が未使用）

**傾向（事実）**
- 登録済み42室のうち、予約履歴に登場するのは 13室のみ（31%）
- 未使用の主な例：セミナールーム（定員60名）、研修室（定員40名）、コラボスペース×2、商談室×3、支社会議室×4
- 使用履歴のある部屋に予約が集中し、一部の部屋で競合が発生している

**現象の説明**
部屋の存在・場所・設備が十分に周知されていないか、予約システムの一覧で目に入りにくい状態になっている。特に別館・支社の部屋は全く使われていない。本社3〜5F の一部部屋への集中が顕著。

**改善案**
- 部屋一覧画面に「空きが多い」タグや代替部屋のサジェスト機能を追加する
- Admin 画面に利用率レポートを表示し、担当者が未使用室を把握できるようにする
- 別館・支社の部屋には用途説明（研修・大規模イベント専用 など）を明記し、選びやすくする

---

### 項目6. 予約データの時刻逆転（endTime < startTime）

**傾向（事実）**
- db.json の現行予約 `resmogjdyqx8ub81r`：startTime `12:00`、endTime `10:00`（終了が開始より前）
- 現行システムでこの不正データの登録が通ってしまっている

**現象の説明**
フォームの入力バリデーションが `endTime > startTime` を検証していないため、誤操作でも保存されてしまう。カレンダー表示や予約衝突チェックの計算ロジックが壊れる原因となり、他の予約にも影響が及ぶ可能性がある。

**改善案**
- フォーム側で `endTime <= startTime` の場合にリアルタイムでエラーを表示する
- API 側でも同条件のバリデーションを実施し、不正データの保存を防ぐ
- 既存の不正データ（`resmogjdyqx8ub81r`）は削除またはステータスを `invalid` に変更する

---

### 構造的な課題：「部屋選択の非効率」は単体問題ではない
項目2・項目4・項目5を並べると、共通の根本原因が見えてくる。
**仮説：「知っている部屋・設備の良い部屋」に予約が集中し、他の選択肢が可視化されていない**

| 問題 | 表れ方 | 共通要因 |
|---|---|---|
| 項目2 | r004（設備最良の大部屋）を少人数が占有 | 設備のある小部屋が選ばれない |
| 項目4 | r007 を同一ユーザーが毎週占有 | 使い慣れた部屋の固定化、定期予約機能の欠如 |
| 項目5 | 42室中29室が未使用 | 部屋の存在・用途がシステム上で可視化されていない |

**示唆**

3項目は「予約時の部屋選択がユーザーの裁量のみに委ねられており、システムが適切な誘導を提供していない」という構造的欠如に帰着する可能性がある。

項目2の機能案（設備・人数に基づくレコメンド）はこの構造問題へのアプローチとして、項目5の改善（未使用室への誘導）にも波及しうる。ただし項目4（定期占有）の解消には、別途「定期予約機能」の実装が必要となる。
