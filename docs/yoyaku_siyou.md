# 仕様書：重複予約防止チェック機能

## 1. 機能名・対象範囲

- **機能名**: 会議室重複予約防止チェック
- **対象範囲**:
  - `src/pages/RoomReservePage.tsx`（フォーム送信前のバリデーション）
  - `src/contexts/DataContext.tsx`（`addReservation` 関数内のガード）

---

## 2. 背景・目的

現状、同じ会議室・同じ日時で複数の予約を登録できてしまう。  
これにより、会議室の二重使用が発生し、予約システムとして機能不全となるリスクがある。  
本機能は、フォーム送信前に既存予約との時間帯重複を検出し、ユーザーへ即時フィードバックすることで二重予約を防止する。

---

## 3. 機能概要

予約フォーム送信時（`handleSubmit` 内）、APIコール前に以下を実行する。

1. `DataContext` が保持する `reservations[]` から、同じ `roomId` かつ同じ `date` の予約を抽出する。
2. 抽出した予約それぞれに対して、入力された時間帯と重複するかを判定する。
3. 重複が検出された場合はエラーメッセージを表示し、APIコールを行わずに処理を中断する。
4. 重複がなければ従来通り `addReservation` を呼び出して予約を登録する。

---

## 4. 入力仕様

### フォーム入力値（既存）

| 項目 | フィールド名 | 型 | 形式 | 必須 |
|------|------------|-----|------|------|
| 日付 | `date` | `string` | `YYYY-MM-DD` | 必須 |
| 開始時刻 | `startTime` | `string` | `HH:mm` | 必須 |
| 終了時刻 | `endTime` | `string` | `HH:mm` | 必須 |
| 対象会議室ID | `roomId` | `string` | 内部ID | 必須（URLパラメータから取得） |

### チェック前提条件

- `date`・`startTime`・`endTime` がすべて入力済みであること（既存の必須チェックが先行する）。
- `startTime < endTime` であること（終了時刻が開始時刻より後）。
  - 違反時はエラーメッセージを表示して処理を中断する（後述の「エラー処理」参照）。

---

## 5. 処理内容

### 5-1. 重複判定ロジック

時間帯の重複は以下の条件で判定する（端点が一致する場合は重複とみなす）。

```
既存予約の開始時刻 < 新規予約の終了時刻
  AND
既存予約の終了時刻 > 新規予約の開始時刻
```

文字列の `HH:mm` は辞書順比較で大小関係が成立するため、文字列比較で判定可能。

### 5-2. 処理フロー

```
handleSubmit 呼び出し
  │
  ├─ [必須チェック] 未入力項目あり → alert("すべての項目を入力してください。") / return
  │
  ├─ [時刻順チェック] startTime >= endTime → alert("終了時刻は開始時刻より後にしてください。") / return
  │
  ├─ [重複チェック]
  │    reservations から roomId === room.id AND date === date を抽出
  │    各既存予約について:
  │      existing.startTime < endTime AND existing.endTime > startTime
  │        → true: alert(重複メッセージ) / return
  │
  └─ addReservation(...) → 成功時: alert("予約しました。") → navigate('/reservations')
                         → 失敗時: alert("予約に失敗しました: ...")
```

### 5-3. 実装箇所

重複チェックは `RoomReservePage.tsx` の `handleSubmit` 内、既存の必須チェックの直後に追加する。  
`DataContext.addReservation` 内には追加しない（DataContext は UI ロジックを持たない方針）。

---

## 6. 出力仕様

| 判定結果 | ユーザーへの出力 | 後続処理 |
|---------|--------------|---------|
| 重複なし | なし（処理続行） | `addReservation` を呼び出し予約登録へ |
| 重複あり | `alert` でエラーメッセージ表示（後述） | APIコールを行わず `return` |
| 時刻順不正 | `alert` でエラーメッセージ表示 | APIコールを行わず `return` |

エラーメッセージ文言：
- 時刻順不正：`"終了時刻は開始時刻より後にしてください。"`
- 重複あり：`"この会議室はすでに指定の時間帯に予約が入っています。別の日時を選択してください。"`

---

## 7. エラー／例外処理

| ケース | 対応 |
|--------|------|
| `startTime >= endTime` | alertで通知しフォームに留まる |
| 既存予約との時間帯重複 | alertで通知しフォームに留まる |
| `reservations` ロード中（`loading === true`）に送信 | 既存の必須チェックで入力不完全が先行するため、通常は発生しない。万一発生した場合もチェック対象配列が空になるだけで、処理フローに影響しない |
| API 登録失敗（既存） | `catch` で `alert("予約に失敗しました: ...")` |

## 9. テスト観点

### 正常系

| # | シナリオ | 期待結果 |
|---|---------|---------|
| T-01 | 既存予約と日付が異なる → 登録 | 予約登録成功 |
| T-02 | 同日・同室だが時間帯が完全に前に非重複（例: 既存 09:00-10:00、新規 10:00-11:00） | 予約登録成功（端点一致は重複扱いしないため） |
| T-03 | 同日・同室だが時間帯が完全に後に非重複（例: 既存 13:00-14:00、新規 10:00-12:00） | 予約登録成功 |
| T-04 | 異なる会議室・同日同時間帯 | 予約登録成功 |

### 異常系

| # | シナリオ | 期待結果 |
|---|---------|---------|
| T-05 | 同日・同室・完全に同じ時間帯 | アラート表示、登録されない |
| T-06 | 同日・同室・既存予約に前から被る（例: 既存 10:00-12:00、新規 09:00-11:00） | アラート表示、登録されない |
| T-07 | 同日・同室・既存予約に後ろから被る（例: 既存 10:00-12:00、新規 11:00-13:00） | アラート表示、登録されない |
| T-08 | 同日・同室・新規が既存を完全に包む（例: 既存 10:00-11:00、新規 09:00-12:00） | アラート表示、登録されない |
| T-09 | `endTime <= startTime` で送信 | 時刻順エラーのアラート表示、登録されない |

## 10. 制約・補足事項

- **判定タイミング**: クライアントサイドのみで完結する。サーバー（json-server）側には重複チェックロジックを追加しない。
- **端点の扱い**: 開始時刻と終了時刻がちょうど一致する隣接予約（例: 既存 10:00-11:00、新規 11:00-12:00）は重複とみなさない。
- **日付をまたぐ予約**: 本システムでは `startTime < endTime` を前提とし、日付またぎ予約は対象外とする。
- **並行アクセス**: 複数ユーザーが同時に同じ会議室を予約するレースコンディションは、json-server の性質上防止不可能。本チェックはベストエフォートの UX 改善として位置づける。
- **`reservations` の鮮度**: チェックには `DataContext` がメモリ上に保持する `reservations[]` を使用する。ページ遷移時に `reload()` が実行される設計であり、通常は最新状態が反映されている。
