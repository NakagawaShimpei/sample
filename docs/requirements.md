# WE研修サンプルアプリ 要件定義

## 概要

WE（ワークプレイスエクスペリエンス）商品の理解を深めるための研修用サンプルアプリ。  
新人研修（3日間）の題材として使用する。

## 研修での使われ方

| Day | 使われ方 |
|---|---|
| Day 1（4/27） | アプリを動かして理解し、改善案を考え、初実装を体験する |
| Day 2（5/11） | 2週間前のコードを読み解き、Claude Codeで改善を進める |
| Day 3（5/12） | 実装を仕上げ、As-Is/To-Beを整理して発表する |

## 技術スタック

- フロントエンド: React + TypeScript（Create React App）
- モックバックエンド: json-server（`db.json` をDB代わりに使用、REST APIを自動提供）
- プロセス起動: concurrently（`npm start` で フロント＋API を同時起動）

### 起動

```bash
npm start
```

- フロント: http://localhost:3000
- API: http://localhost:3001（`/rooms`, `/reservations`, `/devices`, `/loans`）

### データの永続化

- 書き込みは `db.json` に即時反映される（リロードしてもデータが残る）
- 初期状態に戻したい場合は `db.json` を編集するか、git で復元する

## 機能要件

### 1. 会議室管理

| # | 機能 | 説明 |
|---|---|---|
| 1-1 | 会議室一覧 | 部屋名・定員・設備・空き状況を一覧表示 |
| 1-2 | 会議室予約 | 日付・開始/終了時刻・人数・会議名・予約者名・参加者を入力して予約 |
| 1-3 | 予約一覧 | 自分の予約を一覧表示 |
| 1-4 | 予約キャンセル | 予約を取り消す |
| 1-5 | 会議室登録 | 会議室名・場所・キャパ・設備を入力して登録 |

### 2. デバイス管理

| # | 機能 | 説明 |
|---|---|---|
| 2-1 | デバイス一覧 | デバイス名・種類・ステータスを一覧表示 |
| 2-2 | デバイス貸出 | デバイスを借りる（ステータスを「使用中」に変更） |
| 2-3 | デバイス返却 | デバイスを返す（ステータスを「利用可能」に変更） |
| 2-4 | デバイス登録 | デバイス名・場所・管理番号・デバイス種別を入力して登録 |

### 3. ユーザー管理（管理者のみ）

| # | 機能 | 説明 |
|---|---|---|
| 3-1 | ユーザー一覧 | ユーザー名・表示名・ロール・パスワードを一覧表示 |
| 3-2 | ユーザー登録 | ユーザー名・パスワード・表示名を入力して登録（ロールは「利用者」固定） |
| 3-3 | ユーザー削除 | 利用者ロールのユーザーを削除（管理者・自分自身は削除不可） |

※ 会議室管理とデバイス管理は独立（連携なし）

## ロール定義

### ロール一覧

| ロール | 説明 | モック認証情報 |
|---|---|---|
| 利用者 | 予約・貸出を行う一般ユーザー | user / user123 |
| 管理者 | 会議室・デバイスの管理を行う | admin / admin123 |

| 全員の予約を見る | | ✓ |
| 会議室を登録・削除する | | ✓ |
| デバイス一覧を見る | ✓ | ✓ |
| デバイスを貸出・返却する | ✓ | ✓ |
| 全員の貸出状況を見る | | ✓ |
| デバイスを登録・削除する | | ✓ |
| ユーザーを一覧・登録・削除する | | ✓ |

## 利用履歴データ（研修設計用メモ）

`db.json` に過去3ヶ月分の履歴データを仕込んでいる。
新人が `db.json` を直接見た時や API を叩いた時に、以下のパターンを発見できるように設計。

| コレクション | 件数 | 仕込んだパターン |
|---|---|---|
| `reservationHistory` | 59件 | 第1会議室・大会議室Aが人気集中 / 集中ブースはほぼ未使用 / キャンセル率約20% / 10-12時・14-16時に集中 |
| `loanHistory` | 30件 | ノートPCが圧倒的多数 / PCの平均貸出時間が長い / ヘッドセットは貸出ゼロ |

**分析ページは意図的に未実装。** 「このデータから何が見えるか？分析画面があると便利では？」という気づきを新人に委ねる。

## 意図的に不完全にする箇所（研修設計用メモ）

新人に「気づいてほしい」UX上の課題。バグではなく改善余地として設計する。

### UX・画面設計

| # | 不完全な箇所 | 期待される気づき |
|---|---|---|
| A | クラシックなUI（マテリアルデザイン等を使わない） | 「今風のUIに改善したい」 |
| B | 検索・フィルタ機能がない | 「43件をスクロールで探すのは辛い」 |
| C | ソート機能がない | 「定員順・場所順で並び替えたい」 |
| D | ページネーションがない（全件表示） | 「件数が増えたら画面が長くなる一方では？」 |
| E | ログアウトボタンがない | 「どうやってログアウトするの？」 |
| F | 操作完了の通知が `alert` ポップアップのみ | 「画面内に自然なフィードバックが欲しい」 |
| G | モバイル非対応（レイアウトが崩れる） | 「スマホで使えないの？」 |

### 機能・業務ロジック

| # | 不完全な箇所 | 期待される気づき |
|---|---|---|
| H | 会議室の重複予約チェックがない | 「同じ部屋・同じ時間に複数予約できてしまう」 |
| I | 定員を超えた人数で予約できる | 「4名部屋を20名で予約できてしまう」 |
| J | 予約の編集機能がない | 「時間を変えたい時はキャンセルして再予約するしかない」 |
| K | 空き状況が「本日」のみ表示 | 「来週の空きを事前に確認する方法がない」 |
| L | 貸出期間の上限がない | 「いつまでも返却しなくてよい状態になっている」 |
| M | 送信ボタンを連打すると二重登録される | 「同じ予約が2件入ってしまう」 |

### セキュリティ

| # | 不完全な箇所 | 期待される気づき |
|---|---|---|
| N | パスワードが平文でDBに保存され、画面にも表示される | 「ハッシュ化すべきでは？画面に出すべき？」 |
| O | パスワードの強度チェックがない | 「1文字でも登録できてしまう」 |
| P | ユーザー名の重複チェックがない | 「同じユーザー名が2件登録できてしまう」 |

|---|---|---|
